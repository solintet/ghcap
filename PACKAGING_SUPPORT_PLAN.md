# ghcap cross-platform distribution plan (v0.0.29.8 implementation)

This document is a proposed packaging matrix, not a claim that every artifact is already generated by this source archive. ghcap is a terminal application and relies on the separately installed `git`, `gh` (GitHub CLI), and `gpg` commands. Installers must clearly document those runtime dependencies rather than implying that ghcap bundles them.

## Recommended formats

| Platform / channel | Artifact | Feasibility from Debian workstation | Recommended build location | Notes |
|---|---|---:|---|---|
| Windows x64 | Standalone `.exe` | Possible with a GNU cross toolchain; validate on Windows CI | Debian cross-build plus Windows CI, or Windows runner | Prefer MSVC-target builds on Windows for the most native result; GNU target is practical for cross-builds. |
| Windows | `.msi` | Technically possible with extra tooling, but not the best local-only target | `windows-latest` CI runner with WiX tooling | Installer packaging, install paths, uninstall, and runtime dependencies need testing. |
| Windows | `.exe` installer | Possible | Windows CI runner with NSIS or another supported installer builder | Distinguish an installer `.exe` from the standalone `ghcap.exe`. |
| Windows / winget | winget manifest | Yes, as generated metadata; it is not a binary package format | CI generates manifest; submit/update in `winget-pkgs` or a maintained source | Requires stable release URLs, hashes, version and installer metadata. |
| macOS Intel | Architecture-specific `.tar.gz` | Not as a native binary directly from Debian | Manually triggered macOS CI runner | Build `x86_64-apple-darwin`; artifact remains Intel-only. |
| macOS Apple Silicon | Architecture-specific `.tar.gz` | Not as a native binary directly from Debian | Manually triggered macOS CI runner | Build `aarch64-apple-darwin`; artifact remains Apple-Silicon-only. No `lipo` merge. |
| macOS distribution | Architecture-specific archive | Yes, as an artifact | Manual GitHub Actions workflow | The workflow creates Intel and Apple Silicon archives separately; publishing a release is a separate step. |
| Debian / Ubuntu | `.deb` | Yes; existing packaging path | Debian/Ubuntu runner or the Debian workstation | Keep and test the existing native package. Consider separate packages per architecture. |
| Fedora / RHEL-family | `.rpm` | Possible with RPM build tools | Fedora/RPM container or CI runner | Build and test against the target distro; dependency names and policies differ from Debian. |
| Linux general | `.AppImage` | Possible with extra tooling | Linux CI runner | Can package a CLI, but AppImage is more commonly useful for desktop apps. `git`, `gh`, and `gpg` still need a documented strategy. |
| Arch Linux | `.pkg.tar.zst` | Possible with an Arch build environment, not recommended as a raw Debian-native build | Arch container/runner using `makepkg` | Maintain a `PKGBUILD`; build in an Arch environment and validate package metadata. |

## Suggested rollout

1. First establish a CI release matrix and verify the standalone binaries: Linux x86_64, Windows x64, separate macOS Intel and Apple Silicon binaries.
2. Keep `.deb` as the first native Linux package, then add RPM and Arch `PKGBUILD`/package builds.
3. Add Windows MSI and installer EXE once the runtime dependency/install/uninstall experience is specified.
4. Generate winget manifests from the Windows release archive SHA-256 hash.
5. Upload artifacts only after build, test, package metadata, and checksums pass. Do not claim a format is supported merely because an archive can be produced.

## Important limitation

The formats above are not interchangeable. `.exe` and separate macOS Intel and Apple Silicon binaries are compiled binaries; MSI/AppImage/RPM/DEB/Pacman are packages; winget is a distribution catalog. A release workflow should generate these in platform-appropriate CI jobs rather than trying to make every format directly on one Debian host.
